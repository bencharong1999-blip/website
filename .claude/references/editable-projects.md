# โครงการที่แก้ต่อได้และ cache รายช็อต

ใช้กับงานผลิตไฟล์จริงของเบน เก็บต้นฉบับไว้และทำให้แก้ข้อความ เสียง จังหวะภาพ หรือค่าตั้งได้จากข้อมูลโครงการ ไม่ส่งเพียง MP4 แล้วเรียกว่าแก้ไขได้ ปฏิบัติตาม [กติกาทำงานของเบน](ben-working-standard.md) และคำตอบที่เบนให้แล้วในงานเดียวกัน

## ชุดไฟล์ส่งมอบขั้นต่ำ

- `project/timeline.json`: รหัสช็อต/สินทรัพย์, source in/out, output start/end, speed, crop/fit, transition และลำดับเลเยอร์ ระบุหน่วยวินาทีเริ่มจากศูนย์และ fps ให้ชัด
- `project/settings.json` และ `project/text.json`: ขนาด/fps/สี/codec, ระดับเสียง, ฟอนต์/ไฟล์ฟอนต์, สี/ตำแหน่ง/ขนาดข้อความ และเวลาจริงของแต่ละข้อความ เก็บ SRT/ASS แยกตามฉบับตัด
- `assets/manifest.json`: รหัสเดิม, source ID/URL หรือ local path ที่หาได้จริง, SHA-256, ขนาดภาพ/fps/เวลา, สิทธิ์ใช้เมื่อเกี่ยวข้อง และบทบาทของไฟล์ เก็บต้นฉบับไม่ทับ; ไม่คัดลอกสื่อเข้าแพ็กเกจปลั๊กอิน
- `renders/picture-clean.mp4`: ภาพตัดแล้วก่อนเผาข้อความที่เพิ่มในงานนี้และไม่มีเสียงพากย์ พร้อมไฟล์ภาพสะอาดของกราฟิกที่ใช้ ถ้าข้อความติดจากต้นทางให้ระบุว่าไม่มี clean source
- `audio/narrator.wav`, `audio/music.wav`, `audio/sfx.wav`: stem ที่ใช้จริงแยกกันและตรงจุดเริ่ม/ความยาวของ timeline พร้อม final mix ถ้าไม่ได้ใช้เพลงหรือ SFX ให้บันทึกว่าไม่ได้ใช้ ไม่สร้างไฟล์หลอกหรืออ้างว่าแยกเสียงผสมเดิมออกได้สมบูรณ์
- `scripts/` และ `README.md`: คำสั่ง/สคริปต์ที่รันจริง, รุ่นเครื่องมือ, dependencies/ฟอนต์, วิธี relink ไฟล์ และวิธีสร้าง preview/final เก็บรายชื่อ output และ hash ให้ตรวจว่าเป็นฉบับเดียวกัน
- `cache/` เก็บผลรายช็อตและ manifest ที่สร้างแล้ว พร้อมบันทึกสิ่งที่ตรวจจริง ข้อมูลโครงการกับไฟล์ต้นฉบับต้องพอสร้าง cache ใหม่ได้หาก cache หาย

เมื่อสื่ออยู่ใน Drive หรือที่อื่นและไม่รวมในชุดส่ง ให้บอกตำแหน่ง สิทธิ์เข้าถึง และขั้นตอนนำกลับมาใช้จริง ห้ามอ้างว่าโครงการครบถ้าต้นฉบับหรือฟอนต์ที่ต้องใช้ยังหาไม่ได้

## ใช้ของเดิมก่อนสร้างใหม่

1. ค้น asset manifest, hash, transcript/เวลา, contact sheet, ฟอนต์, เสียง, JSON, script และ output ที่มีอยู่ อ่านเฉพาะส่วนที่ใช้กับคำแก้ ตรวจว่าเป็นไฟล์/ฉบับเดียวกันก่อน reuse
2. แบ่งงานเป็นรายช็อต → clean picture → ข้อความ/ซับ → stems/mix → final mux แก้ text/color โดยใช้ clean picture เดิมเมื่อเวลาไม่เปลี่ยน แก้ช็อตเดียวให้สร้างเฉพาะช็อตนั้นแล้วประกอบใหม่ตามที่จำเป็น
3. ใช้ helper [project_cache.py](../skills/ffmpeg-skill/scripts/project_cache.py) ซึ่งใช้ Python stdlib คัดลอกไป `scripts/project_cache.py` ของโครงการและ import `RenderCache` ในสคริปต์ render ที่อยู่ข้างกัน ตัวช่วยนี้ไม่ตัดต่อเองและยังต้องติดตั้ง FFmpeg/เครื่องมือของ command

```python
from pathlib import Path
from project_cache import RenderCache

root = Path(__file__).resolve().parents[1]
cache = RenderCache(root / "cache", project_root=root)
result = cache.run_cached(
    name="shot-C001",
    inputs=[root / "assets/C001.mp4"],
    settings={"in": 1.0, "duration": 3.0, "ffmpeg_version": "ใส่รุ่นที่ใช้จริง"},
    command=["ffmpeg", "-nostdin", "-y", "-ss", "1", "-i",
             str(root / "assets/C001.mp4"), "-t", "3", "-an", "{output}"],
    output=root / "cache/shot-C001.mp4",
)
print(result["status"])  # cached, rendered หรือ planned เมื่อ dry_run=True
```

รันจากโฟลเดอร์โครงการเดิม ใช้ `project_root` เมื่อต้องย้ายทั้งโครงการ: ตัวช่วยทำพาธภายใน root ให้เทียบข้ามตำแหน่งได้ใน recipe แต่ไม่ได้ย้ายหรือ relink ไฟล์ให้เอง ระบุ input ทุกไฟล์ที่มีผลกับ job รวมฟอนต์ ซับ สคริปต์ และ JSON เฉพาะช็อตนั้น พร้อมค่าตั้งและรุ่นเครื่องมือใน settings อย่าใส่ timeline ทั้งเรื่องในทุกช็อตถ้าไม่จำเป็น เพราะคำแก้ช็อตเดียวจะทำให้ cache ทุกช็อตเปลี่ยน

ตัวช่วยตรวจ hash ของ input/output ก่อน reuse ใช้ argv ไม่ใช้ shell และค่อยแทน output เมื่อ command สำเร็จและได้ไฟล์ไม่ว่าง ผล `rendered` ยังต้อง probe/ตรวจภาพ/ฟังเสียงตามงาน ไม่ใช่การรับรองคุณภาพ ใช้ output คนละพาธสำหรับ job ที่รันพร้อมกัน; ไม่มี lock สำหรับหลาย process ที่เขียน output เดียวกัน

4. เก็บผลรันและคำแก้เป็นเวอร์ชันใหม่ ไม่ลบต้นฉบับเพื่อประหยัดพื้นที่โดยไม่ได้รับคำสั่ง สรุปว่าซ้ำจากไฟล์ใด สร้างใหม่ส่วนไหน และใช้เวลาหรือจำนวนรอบเท่าไรเมื่อวัดได้ ไม่แปลงตัวเลขเหล่านี้เป็นเปอร์เซ็นต์โทเค็นโดยไม่มี usage จริง

## ตรวจปลายทางก่อนส่งลิงก์สุดท้าย

เลือกปลายทางและชื่อฉบับให้จบก่อน upload ใช้ file ID/ลิงก์หลักหนึ่งชุดต่อเวอร์ชันของ final render เก็บ final ใน `05_ไฟล์พร้อมเผยแพร่` ใต้โครงการที่ถูกต้อง แยกไฟล์โครงการ/timeline/scripts/stems และ cache จาก final และจาก `02_ฟุตเทจต้นฉบับ` ใช้ parent ID ที่ตรวจจริง; ชื่อโฟลเดอร์อย่างเดียวอาจซ้ำหรือบอกตำแหน่งไม่ครบ

ก่อนส่งลิงก์สุดท้าย ให้ตรวจตามลำดับ:

1. อ่าน metadata กลับจากบริการของไฟล์จริงหลัง upload/จัดวาง: file ID, ชื่อเต็มพร้อมเวอร์ชัน, MIME type, bytes และ parent ID เทียบกับไฟล์ที่ตั้งใจส่ง รวม hash เมื่อบริการมีข้อมูลหรือเราตรวจได้
2. อ่านรายการในโฟลเดอร์ปลายทางที่ตั้งใจไว้ ยืนยันว่ามี file ID เดียวกันและ parent ตรง ไม่ใช้เพียงข้อความว่า upload/move สำเร็จเป็นหลักฐานว่าจัดวางถูก
3. เปิดลิงก์ไฟล์/โฟลเดอร์และตรวจ breadcrumb ที่ผู้ใช้เห็นว่าอยู่ใต้โครงการและ `05_ไฟล์พร้อมเผยแพร่` จริง ถ้าการเข้าถึงหรือเครื่องมือไม่ให้เห็น breadcrumb ให้ระบุข้อที่ยังไม่ตรวจชัดเจน ไม่อ้างว่าตรวจแล้วจาก metadata อย่างเดียว
4. เมื่อยืนยันการส่งและปลายทางสำเร็จแล้ว จึงเขียน delivery index และ Notion ให้ใช้ชื่อ/เวอร์ชัน/file ID/ลิงก์ที่อ่านกลับเดียวกัน พร้อมเวลาตรวจและขอบเขต QC หากจัดวางยังไม่สำเร็จ ให้บันทึกข้อขัดข้องตามจริงและอย่าทำดัชนีเสมือนว่าส่งสำเร็จ

รายงานสถานะแยกกัน: `rendered` = สร้างไฟล์ได้; `technical-QC` = ตรวจคุณสมบัติและความสมบูรณ์ของไฟล์ตามรายการที่ระบุ; `editorial-reviewed` = มีผู้ตรวจเนื้อหา/ภาพ/เสียง โดยบอกผู้ตรวจและขอบเขตจริง; `published` = เผยแพร่บนช่องทางจริงพร้อมหลักฐาน/ลิงก์โพสต์ สถานะหนึ่งไม่ยืนยันอีกสถานะ ชื่อ `05_ไฟล์พร้อมเผยแพร่` ไม่รับรอง QC การอนุมัติของเบน หรือการโพสต์ ขั้นตรวจนี้เป็นหน้าที่ของผู้ช่วยในงานที่สั่ง ไม่เพิ่มคำถามขออนุมัติใหม่และไม่ขยายสิทธิ์เผยแพร่

หลังส่งลิงก์แล้วให้คงชื่อ ที่อยู่ และ file ID ของฉบับนั้น ไม่ rename/move ซ้ำเพียงเพื่อปรับการมองเห็น ส่งลิงก์ตรงและเส้นทางที่ตรวจแล้วเพื่อช่วยค้นหา หากมีการแก้เนื้อหาหรือต้องออกฉบับใหม่ ให้กำหนดเวอร์ชันชัดเจน ระบุ file ID/ลิงก์ใหม่และ ID ฉบับที่ถูกแทนที่ในดัชนีหลังตรวจสำเร็จ เก็บฉบับเก่าโดยไม่ทำให้ผู้ใช้สับสนว่าลิงก์ใดคือฉบับล่าสุด

## ขอบเขตการแก้ต่อ

JSON + script เป็นโครงการที่แก้และสร้างซ้ำได้ด้วย workflow นี้ ไม่ใช่ native project ของ CapCut และไม่รับรองว่าเปิดเป็นเลเยอร์ในแอปมือถือได้ ข้อความที่เผาใน MP4 แก้เป็นเลเยอร์ข้อความไม่ได้; ต้องแก้ text/SRT/ASS แล้วสร้างจาก clean picture หรือทำใหม่จากต้นฉบับ

เปลี่ยนความยาวคำพูด/ช็อตหรือ speed อาจทำให้ตำแหน่งซับ transition เสียงและเพลงเปลี่ยน ต้องปรับตามเวลาจริงแล้วตรวจใหม่ การ export 1080×1920 หรือ 60 fps ไม่กู้รายละเอียดที่หายไปจากต้นฉบับ ไม่เพิ่ม motion จริงให้แหล่ง 30 fps และไม่รับรองว่าฟิลเตอร์ sharpen จะทำให้ทุกช็อตคมเท่ากัน
